Sign in with
your own provider.

GlassKeep works with any OpenID Connect provider. An administrator allows it once; each user then declares their own provider in their settings, links their account to it and signs in through it. This guide covers Authentik, Keycloak and Authelia, with the exact values to enter on both sides.

Overview

Three steps,
two sides.

Single sign-on involves GlassKeep and your identity provider. The order below avoids going back and forth between the two.

1

Allow it

An administrator turns on Allow single sign-on in the admin panel. There is nothing else to configure at instance level.

2

Declare your provider

In Settings, Security, enter the provider's issuer, client ID and client secret. Then link your account by signing in at the provider once.

3

Sign in

On the login screen, choose Sign in with my provider, give your GlassKeep username or email and authenticate at the provider.

Four things to have in place

GlassKeep served over HTTPS

Most providers refuse a plain http redirect address, and credentials would otherwise travel unencrypted.

Configuration from the address your users use

GlassKeep reads its own public address from the page you are on. Open it at your domain, not at a local IP, before filling in the form.

A provider reachable from the GlassKeep server

Not only from your browser. For an account that is not an administrator, the provider must also sit on a public address: the server refuses to connect to a local network address on a user's behalf.

A provider opens only the account that linked it

Identities are matched on issuer and subject, never on e-mail. A provider cannot create accounts or grant any right.

From zero to signed in.

Allow single sign-on

Administrators only. The switch is in the admin panel, under Login page settings. Turning it off hides the button and stops every provider sign-in; each user's configuration is kept for when it comes back.

Written against authentik 2026.8. Labels can differ slightly on other versions.

2a

Start a new application

In the admin interface, open Applications, Applications and choose New Application. Name it GlassKeep. The slug becomes part of the issuer URL, so keep glasskeep.

authentik
2b

Choose OAuth2/OpenID Provider

GlassKeep speaks standard OpenID Connect, so the generic provider type is the right one.

authentik
2c

Configure the provider

Pick an authorization flow: implicit-consent signs users straight in, explicit-consent asks them to approve each time. Leave the client type on Confidential. authentik generates the client ID and the client secret on this page: copy both.

authentik
2d

Restrict the grants and add the redirect URI

authentik enables several grant types by default; keep Authorization Code only. Add one redirect entry in Strict mode with the type Authorization and GlassKeep's callback address. The signing key defaults to the self-signed certificate, which gives RS256.

authentik
2e

Create it and read the issuer

Finish the wizard with Create Application, then open Applications, Providers and the provider you just made. Copy OpenID Configuration Issuer exactly as shown, trailing slash included.

authentik

Optional: choose who can use the application

With no binding, every authentik user can authenticate to the application. That does not weaken GlassKeep, which only opens the account that linked an identity, but you may prefer to list the application for specific people. Open the application, Policy / Group / User Bindings, Create or bind. Click Bind a user (or Bind a group) and the wizard moves on; select the user or group and choose Create.

Written against Authelia 4.39. It assumes OpenID Connect is already enabled on your Authelia (an hmac_secret and a signing key under identity_providers.oidc). If it is not, start with Authelia's own OpenID Connect guide.

2a

Generate the client secret

Authelia stores only a hash of the secret. This command prints both: the plain secret (Random Password), which you give to GlassKeep, and the digest, which goes in the configuration.

docker run --rm authelia/authelia:latest authelia crypto hash generate pbkdf2 --variant sha512 --random --random.length 72 --random.charset alphanumeric
2b

Declare the client

Add this entry under identity_providers.oidc.clients and replace the digest with yours. one_factor requires a password only; use two_factor to require a second factor.

identity_providers:
  oidc:
    clients:
      - client_id: 'glasskeep'
        client_name: 'GlassKeep'
        client_secret: '$pbkdf2-sha512$310000$<digest>'
        public: false
        authorization_policy: 'one_factor'
        require_pkce: true
        pkce_challenge_method: 'S256'
        redirect_uris:
          - 'https://notes.example.com/api/auth/oidc/callback'
        scopes: ['openid', 'profile', 'email']
        response_types: ['code']
        grant_types: ['authorization_code']
        token_endpoint_auth_method: 'client_secret_basic'
2c

Restart and check

Restart Authelia and open https://auth.example.com/.well-known/openid-configuration. Its issuer field is the value to enter in GlassKeep, here https://auth.example.com, with no trailing slash. The account that signs in must exist in Authelia's user backend.

What to take back to GlassKeep

  • Issuer URLYour Authelia address
  • Client IDThe client_id you declared
  • Client secretThe plain secret printed in step 2a
3

Declare the provider in GlassKeep

From the address your users use, open Settings, Security, Single sign-on. Any user can do this once an administrator has allowed it.

3a

Fill in the form

Give the provider a name (it only labels your settings), the issuer URL, the client ID and the client secret. The redirect URI at the top is the one to declare at the provider; it and the public address come from the page you are on.

GlassKeep · Settings
3b

Test the configuration

GlassKeep fetches the provider's discovery document and its signing keys. If the issuer you typed differs from the one the provider publishes, the test shows the right value with a button to use it. The client ID and secret are proven when you link the account.

GlassKeep · Settings
3c

Save, then link your account

Linking adds a way into your account, so GlassKeep asks for your password first, then sends you to the provider to authenticate once.

GlassKeep · Settings
3d

Linked

The settings now show the linked identity. You can unlink it or remove the provider at any time. Changing the issuer or the client ID unlinks the account, since it is no longer the same provider.

GlassKeep · Settings
4

Sign in

On the login screen, choose Sign in with my provider and type your GlassKeep username or email. From the profile picker, selecting your profile is enough.

GlassKeep then sends you to your provider and signs you in only if the identity it returns is the one linked to that account. Any other identity is refused, even with the same e-mail address.

Troubleshooting

When it does not work.

The server log states why a sign-in was refused, prefixed with [oidc]. It never logs tokens or secrets.

There is no “Sign in with my provider” button

Either an administrator has not allowed single sign-on, or no account has linked a provider yet. The button appears once both are true.

“No provider is linked to this account”

The username or e-mail does not match an account that has linked a provider. Sign in another way, then link it in Settings, Security, Single sign-on.

“The provider publishes a different issuer”

The issuer must match what the provider publishes exactly, trailing slash included; the test button offers the right value. Behind a reverse proxy, the issuer follows the provider's own hostname settings (for Keycloak, its hostname and proxy-headers options): fix it there, not in GlassKeep.

“The provider could not be reached”

The GlassKeep server, not only your browser, must reach the issuer: check DNS and firewall. A provider with a certificate from a private authority needs that authority trusted by Node (the NODE_EXTRA_CA_CERTS environment variable).

“This provider is on a local network address”

Only an administrator's provider may sit on the local network. For other accounts, expose the provider on a public address.

“Open GlassKeep at the address your provider was set up from”

The configuration was saved from another address. Sign in from that one, or save it again from the current address and update the redirect URI at the provider.

The provider reports a redirect URI mismatch

The redirect URI declared at the provider must equal the one shown in GlassKeep: same scheme, host, port and path.

“You signed in with another identity”

The account authenticated at the provider is not the one linked to this GlassKeep account. Sign out at the provider and sign in with the account you linked.

“This sign-in attempt expired or was started in another browser”

More than ten minutes passed, the server restarted in between, or the browser blocks cookies for GlassKeep. The attempt is tied to the browser that started it.

On the Android app

The provider opens in a separate screen that shares only cookies with the app, then returns to GlassKeep by itself. Use the same server address in the app as the one the provider was set up from.

Security model

What protects your account.

  • Authorization Code flow with PKCE (S256), state and nonce, handled by the certified openid-client library.
  • The ID token is verified against the provider's published keys: signature, issuer, audience, expiry and nonce.
  • The client secret stays on the server and is never sent back to a browser.
  • A sign-in attempt is tied to the browser that started it; the way back into the app is a single-use ticket valid for one minute.
  • Linking requires the account password, and accounts are never matched on e-mail.

Something not working?

Open a discussion or an issue with the error shown and the matching [oidc] log lines. Never post a client secret.
